# 2단계 5장. 요구사항이 바뀌었을 때

> **실행 환경: 도커.** 명령은 컨테이너 안(bash)에서 칩니다. 교안의 PowerShell 명령은 [도커로 실행하기](../docker/00_도커로_실행하기.md)의 명령 대응표(4절)를 보고 바꿔 씁니다. 편집은 Windows 의 VS Code 에서 합니다.

| | |
|---|---|
| 시간 | 2시간 |
| 준비물 | 4장까지 완료. `templates/stage2/CHANGE_요청서.md`, `templates/stage2/tests/test_lending_v2.py` |
| 결과 | 요구사항 변경을 변경 요청서로 정리하고, 기준을 사람이 바꾼 뒤 AI 에게 구현시킨다 |

## 학습 목표
1. 요구사항이 바뀌면 테스트가 어떻게 깨지는지 직접 본다.
2. 변경 요청서를 쓰고, 승인하는 사람과 바꾸는 사람을 나눈다.
3. 기준(테스트)을 바꾸는 일과 구현을 바꾸는 일을 구분한다.

---

## 1. 개념 — 바뀔 때는 기준부터

프로젝트 중간에 요구사항이 바뀌는 것은 흔합니다. 예: "대출 기간 14일을 기록해 주세요." 이때 무턱대고 코드부터 고치면 두 가지 문제가 생깁니다.

- 기준이 바뀌었는데 테스트가 옛 기준을 붙들고 있어서 실패합니다. 실패가 "잘못된 구현" 때문인지 "옛 기준" 때문인지 알 수 없습니다.
- AI 가 기준(테스트)까지 바꿔서 통과시키면, 검증이 아무 의미도 없어집니다.

그래서 순서가 있습니다.

```text
 ① 변경 요청서를 쓴다 (무엇이, 왜 바뀌나)
 ② 사람이 승인한다
 ③ 사람이 기준(테스트)을 바꾼다
 ④ AI 가 구현을 바꾼다 (기준은 고치지 않는다)
 ⑤ 검증하고 저장한다
```

## 2. 따라 하기

### 1단계. 변경 전 상태 확인하기 (10분)

**[PS]**

```powershell
cd C:\harness-lab\library
python verify.py
git status
```

"검증 통과"여야 합니다. 이 상태가 **변경 전의 기준점**입니다.

### 2단계. 변경 요청서 쓰기 (20분)

**[PS]**

```powershell
Copy-Item C:\harness-beginner-tutorial\templates\stage2\CHANGE_요청서.md .
notepad CHANGE_요청서.md
```

요청서의 1번 칸을 채웁니다.

- 요구사항 번호: R3, R4
- 무엇이 바뀌나: 대출하면 `loan_days` 칸에 `14` 가 들어가고, 반납하면 지운다.
- 왜 바꾸나: 대출 기간을 알아야 한다. (이유를 한 문장으로 쓴다)

요청서의 2번 칸(영향을 받는 테스트)은 **직접 찾아 적습니다.** 힌트: 책 모양이 달라지는 테스트를 찾습니다.

### 3단계. 영향 확인하기 (10분)

변경을 구현하기 전에, 새 기준을 옛 구현에 적용해 봅니다. 이것이 "무엇이 깨지는가"를 미리 보는 방법입니다.

**[PS]**

```powershell
Copy-Item C:\harness-beginner-tutorial\templates\stage2\tests\test_lending_v2.py tests\test_lending_v2.py
python -m pytest tests\test_lending_v2.py
```

실패가 나와야 합니다. 몇 개가 실패하는지, 어떤 이름인지 적습니다.

| 실패한 테스트 | 실패 이유 (assert 줄을 읽고 한 문장으로) |
|---|---|
| | |
| | |

> 실패를 보고 "구현이 틀렸다"고 결론 내리면 안 됩니다. 기준이 바뀌었으니 실패는 정상입니다.

### 4단계. 승인하고 기준 바꾸기 (15분)

요청서의 4번 칸(승인)을 채웁니다. 승인은 요청한 사람과 기준을 바꾸는 사람이 함께 확인합니다. 이 과정에서는 **내가 두 역할을 모두 맡지만, 순서는 지킵니다.**

- [ ] 변경 이유를 다시 읽었다.
- [ ] 영향 받는 테스트를 확인했다.
- [ ] 승인 이름과 날짜를 적었다.

승인이 되었으면 기준을 바꿉니다. 옛 테스트 파일을 새 기준으로 바꿉니다.

**[PS]**

```powershell
Copy-Item tests\test_lending_v2.py tests\test_lending.py -Force
Remove-Item tests\test_lending_v2.py
git diff --stat
```

`tests/test_lending.py` 가 바뀐 것이 보이면 정상입니다. 이 변경은 **사람이 한 것**이므로, 커밋 메시지에 "기준 변경(승인됨)"이라고 적습니다.

### 5단계. AI 에게 구현하게 하기 (30분)

**[PS]**

```powershell
opencode
```

**[AI]**

```text
CHANGE_요청서.md 의 1번 변경을 구현해 줘. tests/ 는 이미 새 기준으로 바뀌어 있으니 고치지 마.
계획을 먼저 말하고 내가 "진행"이라고 하면 library.py 만 고쳐 줘.
```

계획을 검토합니다.

- [ ] `library.py` 만 고치겠다고 했는가?
- [ ] `tests/` 를 고치겠다는 말이 없는가?
- [ ] `loan_days` 를 대출할 때 넣고, 반납할 때 지우겠다고 했는가?

맞으면 `진행`. 끝나면 `/exit`.

### 6단계. 검증하고 저장하기 (15분)

**[PS]**

```powershell
python verify.py
git status
```

- [ ] "검증 통과"가 나온다.
- [ ] `git status` 에 `tests/` 가 바뀐 것으로 보이는 것은 **사람이 바꾼 기준** 하나뿐이다.

저장은 변경 이유를 커밋 메시지에 적습니다.

**[PS]**

```powershell
git add -A
git commit -m "5장: 대출 기간 14일 기록 (요구사항 변경 승인됨, 기준은 사람이 변경, R3·R4)"
```

## 3. 확인하기
- [ ] 새 기준을 옛 구현에 적용했을 때 실패하는 것을 직접 봤다.
- [ ] 기준 변경을 사람이 했고, AI 는 구현만 고쳤다.
- [ ] 커밋 메시지에 변경 이유와 승인 여부가 들어 있다.

## 4. 자주 만나는 오류

| 증상 | 해결 |
|---|---|
| AI 가 `test_lending.py` 를 고쳐서 통과시켰다 | 기준 변경은 사람이 한다. `Compare-Object` 로 확인하고 AI 에게 원래대로 되돌리게 한다. |
| 구현 후에도 한두 개 실패한다 | 실패 줄을 읽고, 요구사항 R3 또는 R4 의 어느 문장인지 찾는다. |
| `Copy-Item` 이 파일을 덮어쓰지 않는다 | `-Force` 를 붙인다. |

## 5. 확인 문제
1. 기준을 먼저 바꾸고 구현을 나중에 바꾸는 이유는 무엇인가?
2. 새 기준을 옛 구현에 적용했을 때 생긴 실패를 "구현의 잘못"이라고 하면 왜 틀린가?
3. 요청서의 "승인" 칸이 없으면 어떤 위험이 생기는가?
